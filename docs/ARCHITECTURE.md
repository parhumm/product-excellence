# Architecture

The local FastAPI service serves the console and JSON API. PostgreSQL stores versioned mission snapshots and run records. A single asynchronous worker launches a Playwright browser, installs deterministic collectors, applies the network profile, observes a page, asks a subscription CLI for a schema-validated action, checks that action and executes it. Every run owns an independent browser context.

Browser input is untrusted. The AI receives bounded observations and screenshots, cannot submit arbitrary browser scripts, and does not control the local service. CLI subprocesses receive structured schemas, restricted tool configuration, separate temporary directories and deadlines. Explicit policy rejects unsafe controls and browser requests before execution. Source files are never exposed as web routes.

Prompts are assembled in `engine/prompts.py`. It drops fields the model cannot act on, encodes a repeated observation as a reference to an earlier one with a decoding note, and leaves every screenshot, measurement, action and finding intact, so compaction saves characters without removing evidence. `engine/pricing.py` holds the selectable model catalogue and published list prices. Only full model ids are offered, because the installed Claude CLI's short aliases resolve to another family. Each call records the model the client reported for that call, its token classes and a cost estimate; the run record carries them as `ai_usage` per call and `ai_totals` for the run. An unpriced model is reported as unknown and marks the total partial, never as zero. Nothing here is billed per call: runs execute on a subscription and the estimate exists only to compare runs.

Deterministic evaluators produce observed rule findings. An AI evaluation pass supplies product hypotheses and visual observations. A separate critic challenges a bounded subset. Content fingerprints deduplicate within a run and connect replay/comparison results. The implementation stores both findings and original evidence IDs rather than treating prose summaries as evidence.

A workspace is an existing project record rather than a new kind. `/api/state` and `/api/findings` take an optional project id and filter missions, runs, schedules and findings before the run cap applies, so a smaller website is not starved by a larger one. Networks, egress routes and personas stay global.

Workspace records can live on a shared team server instead of the local database. `hub.py` is that server: a separate FastAPI process that imports store, contracts and presets but never the runner, Playwright or the AI modules, so it stores and serves data and never executes a mission. `engine/hub.py` is the client half, holding the connection configuration, the HTTP client and artifact transfer; `engine/store.py` routes projects, missions, versions, runs and schedules to it and keeps everything else local. Mode follows the workspace logins: with none the app is the local tool it has always been, and signing out of the last workspace returns to local data rather than silently mixing the two. Execution stays on the machine that starts the mission, on that person's own subscription CLI.

Records carry a `workspace` and an integer `revision`. The server derives the workspace from the authenticated credential and puts it in every read, update and delete predicate, so one workspace cannot reach another's records or evidence. Writes are conditional on the expected revision, which turns a simultaneous edit into one success and one 409 instead of a lost change, and lets a queued run be either cancelled remotely or started by its owner, never both. Each machine holds a random origin id and recovers only runs it owns; an absent origin is unowned rather than assumed local, so one person's restart cannot interrupt another's run and an imported schedule does not execute unexpectedly.

Local evidence stays the durable copy until the server confirms it. A run's terminal status is published only after every referenced artifact is uploaded and its checksum verified, and a failed transfer leaves a pending record under `data/pending-publication` that survives a restart and retries on reconnect. Remote calls run off the event loop, so a slow server cannot freeze the console or a cancellation. Downloaded evidence is cached per server and workspace under `data/hub-cache`, and authentication is checked before a cached file is served.

`engine/outcomes.py` also rates a finished run. Pillar scores and the executive summary come from the same actionable-finding rule the release gate uses, so a dismissed or rejected finding stops counting everywhere at once; both are stored on the run and recomputed when a finding's status changes. A run recorded before scoring existed is rated when it is read, without rewriting stored history. The AI never supplies a number: the review schema asks it only for a headline, prose and next steps, and the deterministic summary stands alone when no worker ran.

Console and page errors keep the error name, stack, source location, page URL and observation step. The stack stays in the stored evidence and in the finding text while the review projection passes only the source location, so prompt size does not grow with stack depth. The finding's rule key is still the message prefix, so fingerprints, replay and comparison keep matching records made before the extra detail existed.

A separate Docker browser optionally supplies Linux netem. Its control service requires a generated bearer token and binds only through host loopback ports. It has NET_ADMIN inside its own container, not host networking. The host orchestrator and subscription clients retain their ordinary network connection. A watchdog clears network settings and closes abandoned browser sessions.

Runtime database files, browser artifacts, persona sessions and proxy credentials are under data and excluded from source delivery. The console has a same-origin mutation boundary and rejects non-local Host headers. The local console still assumes one trusted user on that machine; it has no per-user auth layer. The team server authenticates at the workspace level with HTTP Basic over HTTPS, one shared username and password per workspace, scrypt hashes with their parameters, bounded throttling before hashing, a reserved admin account read from `PEX_HUB_ADMIN_PASSWORD`, and explicit body and upload limits. Networks, egress routes, personas and mission passwords never leave the machine.

A benchmark mission runs the same journey loop once per site: the workspace's own start URL first, then each competitor URL on the mission. Competitor hosts are added to the allowed hosts, but `own_hosts` in `engine/policy.py` stays the narrower set, and only observations on those hosts can carry a finding, so a comparison never fills the workspace's backlog with another company's defects. Each site records its own outcome, reason, evidence id and measurements in `run['sites']`; one site that refuses or fails is recorded as blocked and the remaining sites still run. The AI review receives one observation per site and returns the ranked comparison kept in `run['benchmark']`.

## Important tradeoffs

Plain browser-native JavaScript serves the console without a frontend build pipeline. This differs from the PRD's suggested React/Next.js stack but keeps installation small and actions directly testable. PostgreSQL stores JSON records for flexible early schemas; it is not a high-scale normalized analytics store. Large run histories should be migrated to indexed relational run/step/finding tables before team-scale deployment; the team server adds a workspace/kind index and a server-side run cap, which is enough for a small team and not a substitute for that work.

Workspace credentials are shared, so they grant access and do not identify a person. Machine origin ids coordinate execution between machines; they are not an audit trail and cannot be trusted as one. Per-user roles, individual attribution, remote cancellation of an already running job and offline mission editing are deliberately absent.

Read-only browser policy is stricter than the PRD's proposed staging payment gates. It allows initial browsing without granting financial authority, but blocks workflows requiring mutating endpoints. Actual authenticated/payment success must be verified with dedicated test credentials and a reviewed policy extension.
