# Proxy-Route Switching for "Product Excellence": Design Validation Report

## TL;DR
- **The relay-based design is sound on both platforms, with one blocking caveat**: Android emulator `-http-proxy` is documented (page last updated 2026-03-12, contemporaneous with the netsim rollout) to route "all of the emulated device's TCP traffic" through a CONNECT tunnel — but Google publishes **no** explicit statement that the new netsim Wi-Fi stack (default since emulator 36.5, per the "Change the WiFi packets handler to go through netsimd" closed-issue line) still honors `-http-proxy`. This MUST be verified empirically on 36.6.11.0 before shipping the Android route path.
- **Playwright per-context proxy works on all three engines on macOS; Chromium's loopback handling needs care**: since Chrome 72 Chromium's net stack applies *implicit bypass rules* that send `localhost`/`127.0.0.1` targets DIRECT, and Playwright force-injects `<-loopback>` into Chromium's bypass list (microsoft/playwright #39562). Because your relay's *targets* are public (ipify, the site under test) this does not break relay reachability. A route switch affects only NEW TCP connections on both platforms; in-flight connections finish where they started.
- **The evidence text is honest but needs one wording fix**: the emulator resolves DNS on the host and the TCP proxy tunnels HTTPS by IP, so CDN/geo can follow the *host resolver's* country rather than the exit IP. The "UDP/QUIC not proxied" caveat is correct and confirmed; add a DNS caveat.

## Details

### Q1 — Android emulator `-http-proxy`: transparent for all guest TCP?
**Version: Android Emulator 36.6.11.0 (Homebrew android-commandlinetools), API 34 arm64 AVD, macOS.**

**Documented behavior (developer.android.com/studio/run/emulator-networking-proxy, updated 2026-03-12) — CONFIRMED:**
- The "Emulator Proxy" (what `-http-proxy` configures) "operates at a lower network level and routes all of the emulated device's TCP traffic through the specified proxy." The feature table states it *Handles Non-HTTP/HTTPS Traffic: **Yes** — Forwards all TCP traffic*, and *HTTPS Debugging: **No** — Creates a TCP tunnel, preventing SSL inspection.*
- **Non-443/80 ports**: forwarded (all TCP). **WebSockets and HTTP/2-over-TLS**: ride inside the same TCP/CONNECT tunnel (they are TLS-over-TCP), so they are proxied.
- **UDP and QUIC**: NOT proxied. Docs verbatim: "The Emulator Proxy doesn't support UDP redirection." QUIC (HTTP/3) is UDP and bypasses the proxy entirely. This validates your evidence text "UDP/QUIC not proxied."
- **DNS — hostnames or IPs?** The guest resolves DNS via the emulated DNS server (10.0.2.3 on legacy slirp), which the emulator backs with the *host's* resolver (macOS `/etc/resolv.conf`; the emulator ignores `/etc/hosts`). For plain HTTP the emulator "transparently rewrites HTTP requests," so an HTTP proxy sees the Host header; for HTTPS via CONNECT the proxy sees the destination **IP:port**. So for HTTPS the upstream proxy generally sees IPs, and hostnames are resolved host-side — the crux of Q7.
- **`http_proxy` environment variable**: CONFIRMED read. Docs verbatim: "Define the `http_proxy` environment variable with your proxy settings. The emulator checks for this variable at startup and uses its value automatically if it is defined." Lowercase `http_proxy` is documented; uppercase `HTTP_PROXY` is used only by third-party Docker wrappers, not confirmed for the core emulator. Since you pass `-http-proxy` on the command line, set no proxy env vars to avoid ambiguity.
- **`settings get global http_proxy` in the guest**: expected `null`. `-http-proxy` (Emulator Proxy) is host-side/network-layer and, per docs, is "mutually exclusive" with the Android System Proxy; it does not write `Settings.Global.HTTP_PROXY`. (Well-supported inference from the documented System-Proxy/Emulator-Proxy separation; not a directly quoted command transcript.)
- **Guest observation on refused/timed-out CONNECT**: no Google primary source. Third-party reports (mitmproxy #6803, Proxyman #2493, Fiddler forums) on the adjacent *system-proxy* path show a refusing/closing proxy → connection-reset-type error surfaced fairly quickly (`ERR_CONNECTION_RESET`); a closed port → `ERR_PROXY_CONNECTION_FAILED`; a silently-dropping proxy → the guest **hangs** until a long client timeout. Your relay should therefore return `502` promptly on upstream non-2xx and close cleanly on upstream connect failure so the guest sees a fast reset rather than a hang.

**The material risk — netsim Wi-Fi (UNCONFIRMED; may CONTRADICT assumption):**
- Emulator **36.5** (36.5.10 Stable, 2026-04-02) shipped a new networking stack. Google's "Android Emulator 36 Closed Issues" release notes (developer.android.com/studio/releases/fixed-bugs/emulator/36) contain the verbatim line: **"Change the WiFi packets handler to go through netsimd."** The network-address doc notes that only "in Android Emulator versions earlier than 36.5" did each instance run "behind a virtual router or firewall service" — i.e., the per-instance slirp NAT that `-http-proxy` historically hooked was retired at 36.5. The emulator-console doc corroborates: "Starting with Android Emulator 36.5 and later, Wi-Fi connection traffic is handled by netsim by default. The network capture console command only captures legacy cellular/WAN traffic routed through the QEMU slirp stack."
- Google publishes **no** release note, doc statement, or Issue Tracker entry confirming that netsim-handled Wi-Fi still routes through `-http-proxy`, and none confirming it bypasses it. The proxy doc, updated post-netsim (2026-03-12), still presents `-http-proxy` as fully functional with no netsim caveat — a strong argument-from-silence that it still works, but not proof.
- **Known `-http-proxy` bugs 34.x–36.x**: Issue #314614435 "`-http-proxy` switch is parsed incorrectly," fixed in 34.1.20 and 34.2.13 (April 2024). No confirmed 35.x/36.x regression specific to netsim.

**Verification gate (blocking):** launch `emulator @<avd> -http-proxy http://127.0.0.1:PORT -verbose` against a logging relay; confirm the relay receives CONNECT for arbitrary-port guest TCP; run `adb shell settings get global http_proxy` (expect `null`). If the relay sees no traffic, netsim is bypassing `-http-proxy` and you must fall back to a system-proxy or VPN-based approach.

### Q2 — Emulator console `network speed`/`network delay` at runtime
**Version: same emulator; these console commands are stable across 30.x–36.x.**
- **Applies immediately to live connections**: CONFIRMED. Docs: "To make changes to network speed while the emulator is running, connect to the console and use the `network speed` command" (same for `network delay`). Use the telnet console or `adb emu network speed …` / `adb emu network delay …`.
- **Numeric forms**: `network speed <up> <down>` in **kbps** (e.g., `network speed 14.4 80`), or `network speed <num>` for symmetric. `network delay <min> <max>` (or `<num>`) in **ms**.
- **Exact `network status` output — CONFIRMED, matches your parser:**
  ```
  Current network status:
      download speed:   6000 bits/s (0.7 KB/s)
      upload speed:     6000 bits/s (0.7 KB/s)
      minimum latency:  8000 ms
      maximum latency:  8000 ms
  ```
  Your parser expects lines containing `download speed:` and `minimum latency:`/`maximum latency:` — **this is correct, no change needed.** Two subtleties: (a) speeds are echoed in **bits/s** with a KB/s parenthetical even though you *set* them in kbps; (b) latency is a single min/max pair (no separate upload-latency line). Your `down_mbps`/`up_mbps` → kbps (×1000) and `latency_ms` → `network delay` mapping is right.
- **Shaping while `-http-proxy` is set**: the console help scopes `network` to "ethernet and cellular only." Historically shaping rode the slirp/cellular path. With netsim now carrying Wi-Fi (36.5+), the `network` verb may shape only the legacy WAN path and **not** netsim Wi-Fi — the same netsim caveat as Q1. Verify that `network delay`/`speed` visibly affect Wi-Fi traffic on 36.6. Shaping composes with proxying only if both act on the same guest NIC.

### Q3 — Playwright 1.62 per-context proxy on macOS
**Version: Playwright 1.62 (Python), Chromium/Firefox/WebKit, macOS.**
- **Per-browser support**: CONFIRMED for all three engines, both at launch and per-context. Playwright Python docs verbatim: "You can optionally specify username and password for HTTP(S) proxy, you can also specify hosts to bypass the proxy for."
- **`http://127.0.0.1:PORT` with no credentials**: CONFIRMED accepted. `{'server': f'http://127.0.0.1:{relay.port}'}` is valid; omit username/password.
- **Chromium localhost bypass — CONTRADICTS naive assumption.** Chromium's official "Proxy support in Chrome" doc (chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md) states: "We call these the implicit bypass rules. The implicit bypass rules match URLs whose host portion is either a localhost name or a link-local IP literal. Essentially it matches: localhost *.localhost [::1] 127.0.0.1/8 169.254/16 [FE80::]/10." To *proxy* a loopback target you subtract them: "If you want traffic to localhost to be sent through a proxy… it can be done by adding the special proxy bypass rule `<-loopback>`. This has the effect of subtracting the implicit [bypass rules]."
  - **Crucial for your design**: bypass rules apply to *request URLs*, not the proxy address. Your relay listens on 127.0.0.1 but the *targets* are public, so Chromium reaches the relay regardless. Playwright additionally force-injects `<-loopback>` into Chromium's `--proxy-bypass-list`; the guard is `PLAYWRIGHT_DISABLE_FORCED_CHROMIUM_PROXIED_LOOPBACK`. Bug microsoft/playwright #39562 (repro on v1.58.2) shows that setting `bypass:'localhost,127.0.0.1'` does NOT override this — `page.goto('http://localhost:8000')` fails with `net::ERR_PROXY_CONNECTION_FAILED` "caused by `<-loopback>` always being added to the --proxy-bypass-list chrome flag." Net effect for you: public targets are unaffected; but a `localhost` *target* through the relay will be proxied (not bypassed), and you cannot make it direct just by listing localhost in `bypass`.
- **`context.set_offline` and `Network.emulateNetworkConditions` under a context proxy**: CONFIRMED both work. `set_offline(True)` cuts the context NIC in front of the proxy (drops connections at the browser layer). `Network.emulateNetworkConditions` (Chromium-only, via CDP) throttles in front of the proxy socket, so speed composes with the relay without extra code — exactly as your design assumes. Firefox/WebKit have no `emulateNetworkConditions`, so on those engines you rely on `set_offline` plus your existing link-shape path.

### Q4 — Forcing new connections after a proxy switch
- **Chromium pooled keep-alive/H2 sockets**: Chromium pools connections process-wide and reuses them across tabs; it does NOT cap pool lifetime by the server's `Keep-Alive` header (confirmed on chromium-dev net-dev list). When the relay closes the tunnel (server-side close), the pooled socket becomes unusable and Chromium opens a new tunnel on the next request; Chromium also *resends* a request that failed on a reused socket, so navigations don't surface the error. A route switch therefore affects only NEW connections; in-flight/pooled connections to the old upstream continue until closed. CONFIRMED this matches your expectation.
- **Cleanest way to force a new tunnel**, in order of reliability: (1) **Relay-side active close** of all live tunnels for the old route inside `switch()` — the next request opens a fresh CONNECT to the new upstream; fully under your control. (2) `context.set_offline(True)` then `False` toggles the NIC and drops pooled sockets. (3) CDP `Network.clearBrowserCache` clears cache, **not** sockets — do not rely on it for this. For a guaranteed clean break, combine relay-side close with an offline toggle.
- **Android OkHttp/Cronet**: OkHttp reuses pooled connections; `connectionPool().evictAll()` closes only *idle* connections (active ones get `noNewStreams=true` and finish). You have no app-side hook into the guest's OkHttp/Cronet pools, so the reliable lever is again **relay-side close**: when you switch upstream, close existing tunnels so the guest's next connection re-tunnels. Existing guest connections finish on the old route. CONFIRMED same semantics as web.

### Q5 — Chaining CONNECT through an upstream HTTP/HTTPS proxy
**Against RFC 9110 §9.3.6 and RFC 9112:**
- **Request**: `CONNECT host:port HTTP/1.1` with `Host: host:port` **identical to the request-target** (RFC 9110 §9.3.6). A real-world bug (mendersoftware/mender #2021) was caused by putting the proxy's address in the Host header — don't. Add `Proxy-Authorization: Basic base64(user:pass)` for authenticated upstreams.
- **Response**: require any **2xx** (canonically `200 Connection established`). RFC 9110 verbatim: "Any 2xx (Successful) response indicates that the sender (and all inbound proxies) will switch to tunnel mode immediately after the response header section; data received after that header section is from the server identified by the request target," and "A CONNECT request message does not have content… a 200 response to a CONNECT requests consists of a header block only." So read headers to the blank line and treat the rest as tunnel bytes; expect **no** body. **407 Proxy Authentication Required** → wrong/missing credentials. Non-2xx → return `502` to the client, per your design.
- **Hop-by-hop hygiene**: `Proxy-Authorization`, `Proxy-Connection`, `Connection`, `Keep-Alive`, `Transfer-Encoding`, `TE`, `Trailer`, `Upgrade` are hop-by-hop and must not be forwarded end-to-end. For **absolute-form plain HTTP** to an upstream proxy, forward the absolute-form request-target (`GET http://host/path HTTP/1.1`) verbatim and let the upstream handle Host; when going **direct**, convert to origin-form (`GET /path`) to `Host:80`. Strip your own `Proxy-Authorization` before forwarding to an origin.
- **TLS to an `https://` upstream then CONNECT**: open the socket with `ssl=True` (TLS to the proxy), then send `CONNECT` inside that TLS channel. Chromium's docs note HTTPS proxies "may negotiate HTTP/2 (but not QUIC)"; for a stdlib asyncio relay, HTTP/1.1 CONNECT over TLS is sufficient. Ensure the SSL context trusts the upstream proxy's certificate (aiohttp's docs warn this same context is used for the tunnel to the proxy).
- **asyncio pitfalls**: use `asyncio.open_connection` for both legs; pump both directions with two tasks copying until EOF. Handle **half-close** (`write_eof()` on the EOF'd direction, let the other finish, then close). Always `await writer.drain()` for backpressure and `writer.close(); await writer.wait_closed()` on teardown. Wrap each pump in try/except and cancel its sibling on error. Your `tests/media_proxy.py` CONNECT pump is a sound starting point; add explicit `wait_closed()` and per-direction EOF handling.
- **Reference implementation**: the Python standard library has **no** forward-proxy server class; the canonical references are the `asyncio` streams docs plus small well-known examples (mitmproxy for structure, aiohttp for TLS-to-proxy trust). Your ~90-line relay is the right scope — nothing to inherit.

### Q6 — httpx 0.28 through the relay
**Version: httpx 0.28.**
- **`proxy=` for an HTTPS target through a CONNECT proxy**: CONFIRMED. `httpx.Client(proxy="http://127.0.0.1:PORT")` (or `httpx.Proxy(...)`) makes httpx issue CONNECT for `https://` targets automatically. Probe: `httpx.get("https://api.ipify.org", proxy=f"http://127.0.0.1:{relay.port}", trust_env=False, timeout=httpx.Timeout(10.0, connect=5.0))`. Note 0.28 uses the **singular** `proxy=` argument — the older `proxies=` mapping was removed; any lingering `proxies=` code will break.
- **Recommended timeouts**: an explicit `httpx.Timeout` with a short `connect` and a modest read/overall, e.g. `httpx.Timeout(10.0, connect=5.0)`. Probe failure should raise and be treated as a step error (your design), not an app defect.
- **`trust_env=False`**: CONFIRMED ignores machine proxy env vars. HTTPX docs verbatim: "This request will be sent directly, as we set `trust_env=False`." It disables `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` (and env SSL/`.netrc`). Set it so the probe only ever uses the explicit relay.

### Q7 — Geo/DNS effects
- **DNS resolved on host, proxy tunnels by IP → CDN geo can follow the host's country**: CONFIRMED. The emulator resolves guest DNS via the host resolver (macOS `/etc/resolv.conf`); the web browser resolves via the OS. When the relay tunnels HTTPS by IP (CONNECT to an IP, or the browser having resolved before CONNECT), the DNS resolver's location — not the exit IP — can determine the CDN edge/anycast POP and the geo-DNS answer. An exit IP in country X with DNS resolved in country Y can land on a country-Y edge, making a naive "exit IP = geography" claim misleading.
- **Web-path nuance**: Chromium's proxy.md notes that with an HTTP proxy, name resolution is deferred to the proxy for CONNECT because Chromium forwards the **hostname** (the doc's *always*-proxy-side wording is stated most emphatically for SOCKSv5: "In Chrome when a proxy's scheme is set to SOCKSv5, name resolution is always done proxy side"). So DNS-follows-proxy holds only when your relay passes the **hostname** to an upstream proxy that does its own resolution — not when the relay resolves locally or goes direct, and not on the emulator, which resolves host-side before the tunnel.
- **Ways to make DNS follow the proxy, and cost**: (1) Always chain to an upstream HTTP proxy and forward the **hostname** in CONNECT (not a pre-resolved IP) — cost: only applies when a real upstream is in play, not "direct." (2) SOCKS5 upstream with proxy-side resolution — cost: you deliberately deferred SOCKS5 chaining, and emulator `-http-proxy` is HTTP-only. (3) A relay-side DNS option resolving targets through the route — cost: added relay complexity, and no help for the emulator, which resolves before tunneling.
- **Is ipify-through-relay a sound verification probe?** Mostly yes: `https://api.ipify.org` returns the exit IP as seen by ipify's server — a correct check that traffic left via the route. Caveats: (a) it verifies exit IP, **not** ISP/ASN identity (your evidence text already says this — keep it); (b) it says nothing about DNS geography; (c) it is a single third-party dependency — add a fallback IP-echo endpoint so a probe failure isn't misattributed. ipify is a reasonable primary probe.

## Recommendations

**Stage 1 — Verify the Android transparency assumption (blocking gate).**
Before enabling the Android route path in `engine/contracts.py`, run: `emulator @<avd> -http-proxy http://127.0.0.1:PORT -verbose` against a logging relay; confirm CONNECTs for arbitrary ports arrive; run `adb shell settings get global http_proxy` (expect `null`).
- **Relay sees traffic** → proceed; design validated for 36.6.11.0.
- **Relay sees nothing** (netsim bypass) → do NOT ship `-http-proxy` for Android. Fallbacks, in order: (a) pin the AVD to the legacy slirp path if a flag to disable netsim Wi-Fi exists for your AVD; (b) use the Android **System Proxy** via `adb shell settings put global http_proxy` pointed at the relay — you flagged this as "leaky," but netsim may force it; it covers apps that honor the system proxy, including Chrome/WebView; (c) VPN-based capture (tun2socks) — highest fidelity, highest complexity. **The single benchmark that decides this: does the relay receive guest CONNECTs on 36.6.11.0.**

**Stage 2 — Web path.** Ship the Chromium relay path as designed: `options['proxy'] = {'server': f'http://127.0.0.1:{relay.port}'}`. Do not add `localhost` to `bypass` expecting it to keep the relay "direct" — it won't change relay reachability (targets are public), and Chromium/Playwright ignore it for loopback anyway. Keep the native Playwright proxy path for web missions with `egress_id` and no route steps (preserves SOCKS5 and the remote netem runner).

**Stage 3 — Force-new-connection on switch.** Implement relay-side active close of old-route tunnels inside `switch()`. This is the one reliable lever that works identically for Chromium pools and guest OkHttp/Cronet pools. Optionally pair with `context.set_offline(True/False)` on web for a guaranteed clean break. Document that in-flight connections finish on the old route.

**Stage 4 — Probe and evidence.** Keep the ipify probe with `trust_env=False` and `httpx.Timeout(10.0, connect=5.0)`; add a second IP-echo fallback endpoint. Treat probe failure as a step error, not an app defect (as designed).

**Stage 5 — Evidence text fix.** Add a DNS caveat. Suggested: `'Connections exit through this route; observed exit IP recorded per switch. UDP/QUIC not proxied. DNS is resolved on the host, so CDN/geo may follow the host resolver's country rather than the exit IP. ISP/ASN identity not independently verified.'`

**Benchmarks/thresholds that would change the design:**
- Relay receives no guest CONNECTs on 36.6 → switch Android to system-proxy or VPN (Stage 1).
- `network status` output ceases to contain `download speed:` / `minimum latency:` → update the parser (currently CONFIRMED correct — no change).
- `network delay/speed` does not affect netsim Wi-Fi → move shaping to netsim args, or accept cellular-only shaping and document it.
- Any Playwright engine ignores per-context proxy → fall back to launch-level proxy for that engine (not currently needed; all three honor it).
- Deliberately-skipped items remain justified: SOCKS5 upstream chaining (unneeded; emulator is HTTP-only anyway), remote-netem relay (refused when route steps exist — correct), runtime `settings put global http_proxy` on a running emulator (leaky — correct *unless* Stage 1 forces the system-proxy fallback, which would revisit this decision).

## Caveats
- The biggest open question — whether netsim Wi-Fi (default since emulator 36.5) still honors `-http-proxy` on 36.6.11.0 — is **not resolvable from public primary sources** and must be tested empirically. The documentation (updated 2026-03-12, post-netsim) still presents `-http-proxy` as fully functional with no caveat, which is suggestive but not conclusive.
- Guest behavior on a refused/timed-out CONNECT is documented only via third-party (system-proxy) reports; the reset-vs-hang distinction is plausible but not from a Google primary source.
- The `settings get global http_proxy` → `null` expectation is a well-supported inference from the documented System-Proxy/Emulator-Proxy separation, not a quoted command transcript.
- Playwright's forced `<-loopback>` behavior is documented via microsoft/playwright #39562 (repro on v1.58.2) and the source guard `PLAYWRIGHT_DISABLE_FORCED_CHROMIUM_PROXIED_LOOPBACK`; confirm on 1.62 specifically that it does not interfere with your public targets.
- httpx 0.28 uses singular `proxy=`; any code still using `proxies=` will break on 0.28.
- The DNS-follows-proxy behavior applies only where the relay forwards hostnames to a resolving upstream; on the emulator, DNS is always resolved host-side before tunneling, so the geo caveat in the evidence text is required, not optional.
