ProductExcellence

Definition

A local console that runs goal-driven browser journeys with a bounded AI worker and records evidence you can challenge.

Boundaries

  • API keys. It drives the Claude or Codex client you already pay for.
  • Writes to the site under test. Mutating requests are blocked and counted.
  • Numbers it did not measure. An unavailable signal is reported as unavailable.

The worker is a language model with no hands. These are the reasons it stays that way.

Bounded by design

The AI chooses the next click. It cannot do anything else.

  1. Safe mode, empty tool set. The Claude client starts with an empty tool set, an empty MCP configuration, no session persistence and a short task-only system prompt. Codex starts ephemeral, ignoring user config, in a read-only sandbox with its shell tool disabled.
  2. Schema-validated actions. The worker answers with one structured action or one evaluation. Anything else is refused, and two refused or malformed answers in a row end the run.
  3. Restricted keyboard. Only navigation keys, plus Enter inside a live search box. Any other key is refused rather than risking an unintended form submission.
  4. Read-only network. POST, PUT, PATCH and DELETE are blocked by default so no account or payment can change. This run had eight requests blocked, and the count is reported so a resulting failure is never blamed on the product.
  5. Domain allow list. The run is confined to the domains the mission names. Everything else is refused at the browser.
  6. Credentials the worker never sees. Public browsing by default. A mission may carry a sign-in, which relaxes the read-only rule for that mission's own domains and nothing else, or use a test session captured deliberately. The password is typed by the engine where the goal writes {{password}}, so it never reaches the worker, the goal, a finding or a report.

Evidence is written on the Mac that ran the test. The worker receives selected observations, not your filesystem. A finished run can be published to a team server your colleagues read; the browser traces stay behind on the machine that ran the mission. Runs are replayable, so a claim made in September can be re-measured in October under the same conditions.

Run it again

One run is an anecdote. The second run is where the argument starts.

Replaying the mission took 134.62 seconds and produced two findings the first run had never seen, thirteen that persisted, and none that disappeared. The interesting one is a measurement, not an opinion.

New in the replay. Severity P2, performance, evidence step-001.

Very slow server response measured when loading the search page.

Observed: the search page load at step-001 recorded a time to first byte of 9,868.6 ms and a DOM loaded time of 12,373.9 ms, compared with 625.9 ms on the homepage at step-000.

Expected: time to first byte for a core navigation page stays in the same order of magnitude as the homepage rather than several seconds.

A second model reviewed this finding against the raw observation and marked it probable, not confirmed, for two stated reasons: the homepage comparison figure was not in the evidence it was given, and a single sample cannot rule out a cold start. A finding a critic has not confirmed costs half as many points. The console shows you the disagreement instead of resolving it silently.

Reason recorded against the blank: "CRO needs an AI review; this run completed none." Performance scored a real zero in the journey run, from six confirmed P2 findings on slow paint and layout shift. The two look nothing alike in the console, and that is the point.

How a score is computed. Printed beside every score in the console.

Each selected pillar starts at 100 and loses points for its open, non-rejected findings (P0 and P1 cost 40, P2 costs 15, P3 costs 5; a finding an AI critic has not confirmed costs half). A journey that did not reach its goal costs Functionality 30. A pillar that was not evaluated is not scored, which is different from scoring zero. This rates the findings recorded in this run. It is not a field measurement or an industry benchmark.

Install

One command, then the subscription you already pay for.

git clone git@github.com:parhumm/product-excellence.git
cd product-excellence
./start.command

The first start installs its own Python, its dependencies and Chromium, Firefox and WebKit, then opens the console. There is no PostgreSQL to set up, no Node, no npm and no API key: a fresh installation records to a SQLite file at data/records.db. Later starts take a second.

Sign in once with claude auth login or codex login, whichever subscription you hold. You need one of the two for an AI worker, and the deterministic checks below run without either.

Missions

Ten missions are waiting the moment you add a website.

Each one is a goal sentence with a mode, a viewport, a network, a step budget and the pillars it judges. They are written for any business, and they are yours to edit.

  1. auditHome page · five-pillar audit
  2. journeyRegister · reach the sign-up form
  3. journeySign in · account access
  4. journeySearch · find something specific
  5. exploreCore features · detect and use
  6. journeyPricing and checkout · up to payment
  7. journeyGet the app · mobile app download
  8. auditSEO and AEO · search and answer readiness
  9. journeyUX, UI and accessibility · keyboard and screen
  10. journeySlow mobile · core task on a poor connection

The ten starter missions are generic and can be adapted to any website you are authorized to test.

Any mission can be re-run under any of these. The same goal, a different connection.

Skills

Or say what you want in a sentence, and let it write the mission.

Open Claude Code in the project folder and type /pex-. Eight skills cover the work around a run: writing one, fixing one, and turning what it found into something a team can act on.

They are bounded the same way the worker is. They never open a saved password, a captured session or a recording. Page text, findings and log lines are treated as data to read, never as instructions to follow. And nothing is imported, run, edited, filed or pushed until you say so. The steps each one takes are plain files in .claude/skills/, readable before you trust them.

Benchmark

The same question, asked of the competition.

A benchmark mission runs its goal on your site and on each competitor you name, then ranks them against each other.

Findings are recorded against the workspace's own site only. A competitor that cannot be observed is reported as blocked rather than as a zero.

Your team

Shared where everyone can read it, run on the machine that owns the subscription.

When a run finishes on your Mac it can publish itself, with its screenshots, its recording, its measurements and its findings, and everyone signed in to that website sees the same record. The console there is read only behind a workspace username and password.

The server stores and shows. It never opens a browser and never calls an AI, so nothing is tested there and no subscription is shared. Tests keep running on each person's own machine.

Two existing workspaces were moved onto a server over the public internet in a single attempt each, thirty-three runs for one site and seventy-five for the other. Every transferred file was read back and checksummed against the original: 944 MB, byte for byte.

Tests run on your Mac at 127.0.0.1:8741. Results can be shared on a team server.
